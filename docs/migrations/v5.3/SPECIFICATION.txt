- All relationships belong in content front matter; no relationship data file.
- Multiple simultaneous employers/affiliations are a normal case; no forced primary.

RULES
- Collection directory PLURAL; list layout PLURAL; detail layout SINGULAR.
- `details/speaker` is a generic person-capable renderer: show Speaker badges,
  talk-specific facts and calls to action only if `person.roles` contains speaker.
  Otherwise use neutral Person/profile copy, never falsely label a speaker.
- `details/member` is a generic organisation-capable renderer: show Member
  badges/tier only for active members; non-members have neutral Organisation
  detail rendering. `lists/speakers` and `lists/members` similarly support
  `listing.filter: all` with neutral titles/card links. See Sections 08, 09, 17.6.
- Post filenames YYYY-MM-DD-<slug>.md; post slug excludes date prefix.
- All other Markdown filenames lowercase kebab-case, .md only.
- `_redirects` records are exceptions: no list layout, normal detail layout,
  title/summary/navigation/image/entity group, forms or Markdown body.
- Redirect `permalink` is the OLD route; `redirect_to` is the NEW target.
- Redirects are generated as minimal HTML documents, not HTTP 301/302.
- Front-matter field keys snake_case; UK English (`organisation`, `programme`).
- Jekyll layout references: `lists/...`, `details/...`, `page/...`.
- List files live under pages/<category>/<subcategory>/<page>.md.
- Detail files live under the collection directory, NOT pages/.
- All page/entity images live under their navigation path and item slug.
- Common images used by several pages live in assets/images/common/.
- Image paths DO NOT imply URL changes; use permalink to preserve URLs.
- New paths have no spaces; case-sensitive, filename/pointer check.
- _posts is special: set post permalink globally or per record, preserving /news/<slug>/.
- Product records live in `_products`; Repository records live in `_repositories`.
- New canonical routes use /products/* and /repositories/*.
- Every migrated record with an old route MUST have ONE verified `_redirects`
  mapping unless its original permalink is retained without change:
  /hardware/<slug>/ -> /products/<slug>/
  /software/<slug>/ -> /repositories/<slug>/
- Legacy directory URLs /hardware/ and /software/ also use `_redirects`.
- Do NOT additionally put redirect_from on the target page for the SAME path;
  duplicate generated output is forbidden. `_redirects` is authoritative.
- Enable and test `jekyll-redirect-from` under GitHub Pages/Jekyll.
- Audit existing `_layouts/redirect.html`: it currently uses the legacy scalar
  page.redirect, while the plugin custom-layout contract is page.redirect.to.
  Use the plugin default layout or adapt the custom layout to the plugin API.
- Update `_config.yml` collections / defaults / navigation as part of migration.
- Preserve old routes for records RECLASSIFIED as ordinary pages as well.
- Source types that are not bona fide Products/Repositories require explicit
  mapping; do not drop certification, technology overview or ecosystem pages.

PROPERTY NAMING — ONE CANONICAL RULE
- Group genuine concepts under a named object, as with navigation.header.
- Within each object, use snake_case for an indivisible property name.
- Repeated records are YAML sequences; document paths with [] notation.
- Do not turn each English word into another level of nesting.
- Do not use dotted YAML keys such as `event.sessions.title:`; dot paths are
  only documentation notation, not literal YAML property names.
- Singular semantic entity containers: post, event, person, organisation,
  publication, product, repository, working_group, guide, policy.
- Plural repeating fields: schedule[], sessions[], presentations[], fields[],
  resources[], forms[], roles[], focus_areas[], prerequisites[].
- Event programme hierarchy: event.schedule[].date,
  event.schedule[].sessions[].title and
  event.schedule[].sessions[].presentations[].title.
- Never flatten a day's session as event_session_title or event.sessions.title.
- Cross-entity associations are nested in the owning record front matter,
  e.g. event.speakers[], person.organisations[], publication.authors[].
- A single descriptive key may use snake_case (job title, date, etc.); choose
  nesting for repeated records, roles, and meaningful composite objects.

DATA CONTRACT
[R] title: canonical display title and H1; never duplicate heading/title.
[R] summary: reusable description for all entity details and ordinary pages.
[O] summary: list-page introduction; omission renders no intro placeholder.
[R] navigation.header.category + subcategory (except category landing).
[R] semantic entity group (post/event/person/organisation/... as defined).
[O] permalink: used for URL stability; listing page normally explicit.
[O] date: ISO quoted on posts and events (required for those entities).
[O] end_date: ISO quoted for single-day events; REQUIRED when event spans
    multiple days, and validated against authoritative event date span.
[O] image: {src, alt, fit}; fit: contain for logos; optional.
[O] resources: flat [{type,label,url}] verified links; event resources may
    also carry one of `session_id` or `presentation_id` (see Section 07).
[O] forms: flat [form_key] references into _data/forms.yml.
[O] navigation.footer.category: only for selected footer links.
[D] reading time, event status, related cards, prev/next guide.
- Redirect records use ONLY the routing-only contract in Section 16, not
  shared entity-detail rules above.

RESOURCE TYPES
website | documentation | repository | download | pdf | slides | video |
publication | recording | external

- No hero, eyebrow, aside, actions or view-position fields in front matter.
- No empty image placeholders; optional fields OMITTED, not empty strings.
- Markdown contains long-form material; body starts with H2 (template H1).
- Template prints facts from semantic YAML; don't repeat in body verbatim.
- `resources` is canonical for document/media/download/source-code and
  general-purpose external link CTAs (PDF, slides, video, repository, etc.).
- Domain-specific links remain on their semantic entities: `event.registration`,
  `organisation.website`, `person.links`, and `form.submission` are allowed
  and MUST NOT be copied into resources solely to create a CTA.
- One destination has one authoritative field; the template may render the
  semantic link as a button without creating a duplicate resource record.
- `resources` type: repository identifies a repository source-code link.
- Resources may contain optional `session_id` OR `presentation_id` only on
  Event records. These map to IDs in that event, are mutually exclusive, and
  are not independent URLs or foreign-key entity relationships.
- Never infer a news-to-organisation relationship from an author's employer:
  Organisation news cards come from explicit `related[]` post links (see 09).
- Original diagrams, illustrations, official PDFs and alt text retained.
- Inline body images preserve Kramdown `{: .image-left }`,
  `{: .image-right }` or `{: .image-full }` placement classes as authored;
  preserve other existing image fit/crop classes with equivalent CSS.
- Hero/portrait/logo uses `image:` front matter and layout defaults, while
  inline image placement lives beside each image in simple Kramdown.
- Moving assets cannot drop alignment/fit or break alt text and caption context.

03 — RELATIONSHIPS / FRONT-MATTER OWNERSHIP / REVERSE VIEWS
==============================================================================

RULE: ALL CONTENT RELATIONSHIPS LIVE IN THE OWNER RECORD'S FRONT MATTER.
- Do not create or read `_data/relationships.yml`.
- Do not maintain relationship arrays on both sides of the association.
- Inverse links and cards are GENERATED by querying owning front matter.
- Use collection slugs as foreign keys; validate every referenced slug.
- Prefer a scalar where one association is genuinely singular.
- Use arrays where multiple entities/roles can occur, even simultaneously.

CANONICAL RELATIONSHIP OWNERSHIP
  Post       post.authors[]                   Person(s), ordered byline
  Person     person.organisations[]           Organisation(s), incl. jobs
  Event      event.organisers[]               Multiple organising organisations
  Event      event.partners[]                 Additional partners/sponsors
  Event      event.speakers[]                 Person + talk/session + role
  Paper      publication.authors[]            Ordered Person(s) / text credits
  Product    product.manufacturer             Organisation, if single/known
  Product    product.repositories[]           Compatible repositories + status
  Repository repository.maintainers[]         Maintaining organisations
  Group      working_group.coordinator         Organisation, if single/known
  Guide      guide.primary_product             Product, if single/known
  Policy     policy.owner                      Organisation, if single/known
  Any page   related[]                         Directed typed content links

PERSON AFFILIATIONS: MULTIPLE CURRENT EMPLOYERS ARE NORMAL
- Use `person.organisations[]`: ONE item for each organisation.
- Each item has `organisation` (slug), `relationship` (employment |
  research | consultancy | governance | other), `positions[]`.
- Every position has `title`, `status` (current | past) and optional
  `start_date` / `end_date` (quoted YYYY-MM-DD); overlapping dates ALLOWED.
- No required or implied `primary` flag; no automatic ranking or single
  employer fallback. Display ALL current affiliations, then historical ones.
- One organisation can have multiple roles/positions, including overlapping.
- Organisational name/logo/URL come from `_organisations/<slug>.md`.
- Do not confuse membership with employment: non-member employers are valid.
- An Organisation's People list is GENERATED by reverse person.organisations.
- A person may also be a speaker, author, director or organiser; these
  are separate roles and do not imply exclusive employment.
- Governing Board membership/order also belongs in Person front matter:
  person.governance.board_order: integer, board_role: optional text.
  Do not use `_data/governing-board.yml` as a live roster after migration.

EXAMPLE: TWO SIMULTANEOUS EMPLOYMENTS (ILLUSTRATIVE PERSON ONLY)
FILE: _people/example-speaker.md
---
layout: details/speaker
title: "Example Speaker"
summary: "Example of two current employers at the same time."
navigation:
  header:
    category: "News & Events"
    subcategory: "People & Opportunities"
person:
  roles: [speaker]
  organisations:
    - organisation: university-of-cambridge
      relationship: employment
      positions:
        - title: "University researcher"
          status: current
          start_date: "2023-01-01"
    - organisation: example-private-company
      relationship: employment
      positions:
        - title: "Company technical director"
          status: current
          start_date: "2024-05-01"
---

- `example-private-company` is a PLACEHOLDER, not a claimed affiliation.
- Both affiliations are current on this sample record, despite overlap.
- Dates are optional; do not invent real employment dates or job titles.
- For a real Person, every organisation must resolve or be explicitly held
  for editorial review. Do not fabricate a company/profile just to link it.

EVENT ORGANISERS + SPEAKERS — EVENT OWNS BOTH ARRAYS
  event.organisers[]:
    - organisation: slug
      role: organiser | co_organiser | host
  event.partners[]:
    - organisation: slug
      role: collaborator | sponsor | exhibitor | partner
  event.speakers[]:
    - person: slug
      role: speaker | moderator | panellist | host
      session: id-of-session-or-presentation

- A single event can have MULTIPLE organiser rows. Do not use organiser: slug.
- Speaker participation is one item per Person + session/presentation + role.
- `event.speakers[].session` resolves into this event's schedule; positions
  come from YAML array order, optionally with an `order` scalar if needed.
- One Person can speak in several slots on the same event.
- Avoid copying speaker information into schedule.sessions[].presentations[];
  the programme contains talk titles/times and `event.speakers[]` links people.
- Event's `organisers` and `partners` are distinct kinds; don't duplicate the
  same role on both arrays. One entity may have genuinely different roles.
- Event speaker cards, Organisation event links, and Person event links are
  generated by reverse queries, not hand-maintained backreferences.
- Example Event slugs `semi`, `example-presenter`, `example-moderator`
  are illustrative references: resolve against real records before launch.
- A sample is not evidence of any individual's real employment or event role.

PAPER / POST AUTHORS
- `publication.authors[]`: ordered entries `{person: slug}`; use `{name: ...}`
  only for real external authors without a Person profile.
- `post.authors[]`: same ordered entries; may add a documented `role`.
- Order is the YAML sequence order, not duplicated `position` fields.
- Person publication/news views are GENERATED by searching author lists.
- Never invent a Person page to make an author relationship work.

PRODUCT / REPOSITORY COMPATIBILITY
- The Product owns `product.repositories[]` with `{repository, compatibility}`.
- Repository's Products panel is an automatic inverse of that same list.
- Repositories do NOT also store a products[] list.
- `repository.maintainers[]` permits several maintaining organisations.

GENERIC RELATED LINKS (OPTIONAL)
---
related:
  - type: guide
    slug: choose-a-platform
    relation: related
  - type: event
    slug: cheritech26
    relation: featured
---

- `related[]` belongs to the source PAGE/ENTITY front matter.
- Do not mirror it on the destination. Reverse links are derived if wanted.
- For Organisation Related News, the Organisation owns explicit `related[]`
  entries with `type: post`; do NOT infer news from staff bylines, affiliation,
  or a post that merely mentions the Organisation. Show no panel if absent.
- Allowed type names map to canonical collections and ordinary page records;
  validate type, slug and destination public URL.
- If category filters create overlapping views, do not duplicate records.

VALIDATION
[ ] Every relationship slug references an output record.
[ ] Every `person.organisations[]` item has an organisation and positions.
[ ] A Person may have two or more `status: current` employment entries.
[ ] No primary employer is auto-selected or required.
[ ] Overlapping employment/affiliation date spans are accepted.
[ ] Current and historical affiliations render with correct labels.
[ ] Event organisers can contain two or more organisations.
[ ] Event speaker session/presentation IDs exist and are unique per event.
[ ] Reverse views on People/Organisations/Events/Papers derive correctly.
[ ] Product compatibility / author ordering are read from owner record.
[ ] Duplicated same-role associations and orphan references rejected.

05.1 — SIMPLE KRAMDOWN MARKDOWN AUTHORING STANDARD

ALL `pages/**/*.md` AND COLLECTION DETAIL MARKDOWN BODIES
- One YAML front matter block at top (--- ... ---); body begins after it.
- `title`, `summary`, navigation, image, entity facts, links/resources,
  schedule and forms live in front matter or reusable _data, NOT repeated.
- Template generates H1/title, summary, breadcrumbs, hero/facts, schedules,
  related cards, forms, global header, footer and newsletter CTA.
- Markdown BODY starts with H2 (`##`); use H3 (`###`) for subsections.
- Do not write a second H1 (`#`) in body; do not skip heading levels.
- Separate paragraphs, headings, lists, tables and images with blank lines.
- Use one Markdown link per URL, meaningful link text; never raw link buttons.
- Use simple relative-to-root site URLs `/guides/.../` for internal links.
- Standard image form: `![Meaningful alt text](/assets/images/.../file.webp)`.
- KEEP image-specific Kramdown classes when used for alignment or fit:
    .image-left   float/align the inline image to the left
    .image-right  float/align the inline image to the right
    .image-full   full-width inline image
  Other existing image-only crop/fit classes must also be preserved and
  remapped to working CSS during migration, not silently stripped.
- The ONE Kramdown attribute-list exception is IMAGE PLACEMENT/FIT; attach
  immediately to its image on the next line:
    ![Diagram](/assets/images/build/technology/diagram.svg)
    {: .image-left }
  Examples: `{: .image-right }`, `{: .image-full }`,
  `{: .image-full .image-contain }` (if both existing styles are needed).
- For PRIMARY hero/portrait/logo image: front-matter `image.src/alt/fit`;
  template controls hero position. Do not duplicate a hero image in Markdown.
- Decorative image? Set image handling in template/front matter; do not
  insert an empty-alt hero/portrait into the Markdown body.
- Tables: ordinary pipe tables with a separator row; short content only.
- Code: fenced code blocks using native Kramdown `~~~ language` fences,
  lowercase syntax languages; inline code uses single backticks.
- Use `-` for bullet lists; `1.` for numbered steps; normal `**bold**`,
  `*emphasis*`, `> quote`, `---` horizontal rules when necessary.
- No raw HTML, inline CSS, `<div>`, `<table>`, `<img>`, `<iframe>`, script,
  arbitrary attributes or hand-built layout/grid/card markup in page bodies.
- No general per-paragraph Kramdown attribute lists: `{: .class }`,
  `{: #id }`, `{: .source-breadcrumbs }`, etc. Only IMAGE-specific
  alignment / fit / crop classes are permitted; keep any existing such classes.
- Do not apply alignment classes to unrelated paragraphs or cards.
- No Jekyll/Liquid logic in content bodies (`{% include ... %}`,
  `{% assign ... %}`, executable `{{ ... }}`); template logic stays in layouts.
  One narrow exception: `{% raw %}` / `{% endraw %}` may wrap literal Liquid
  syntax in code examples so GitHub Pages/Jekyll 3 does not execute it.
  They are escape delimiters, NOT content components or page logic.
- Never handwrite breadcrumbs, repeated card directories or call-to-action
  buttons; templates and front matter generate these.
- Use resource records for download/PDF/repository URLs, not duplicate
  button markup in body. Inline contextual links remain allowed.
- No copied event programme tables: event.schedule is sole timetable source.
- TARGET RUNTIME: the GitHub Pages gem currently resolves Jekyll 3.10.0;
  Jekyll 3 does NOT support `render_with_liquid: false`. Do not rely on it.
- In Markdown content, wrap any fenced/inline code containing literal Liquid
  tokens (`{{`, `{%`) in `{% raw %}` ... `{% endraw %}`. These are the
  ONLY permitted Liquid delimiters in authored bodies; verify exact output.
  If the literal example itself contains `{% endraw %}`, use a separately
  linked code asset or an independently tested escaping strategy.
- Test protected snippets with `bundle exec jekyll build` using the actual
  github-pages Gemfile. Do not rely on a local Jekyll 4-only option.
- Kramdown config remains `markdown: kramdown`, `kramdown.input: Kramdown`.

ROUTE MAPPING RULES
- `_redirects` is the SOLE registry for old routes that are changing.
- Content destination pages do NOT also declare `redirect_from` for those
  same paths. Avoid duplicate output conflicts and split ownership.
- Keep unchanged public URLs as-is; no redirect page is required.
- No list page or homepage card for redirect records.
- Do not include redirect records in search, related content, nav, sitemap.
- No regular site header, footer, breadcrumbs, newsletter CTA or H1.
- No unverified, external, circular, chained or self-referential targets.
- Never redirect an old URL that a live page still occupies.
- Canonical old source may redirect directly to the final destination;
  skip intermediate stages, e.g. old software -> final repositories.
- GitHub Pages Jekyll plugin output is HTML with meta refresh, NOT true
  server-side HTTP 301/302 status. Do not promise status-code redirects.
- Source fragment identifiers (#section) and query strings are fragile;
  test important historical deep links and preserve aliases explicitly.
- Old CSS, image, PDF and file paths: RETAIN/copy static assets as needed;
  a redirect HTML page is not a reliable binary-asset redirect.
- Redirect files are normal `.md` collection documents with YAML only;
  plugin creates the output. Do NOT use special hosting `_redirects` syntax
  (e.g., a Netlify whitespace-delimited redirects file).

JEKYLL / PLUGIN CONTRACT
- `jekyll-redirect-from` already appears in the repository Gemfile.
- Register `collections.redirects.output: true` in `_config.yml`.
- Confirm the plugin is activated under both local and GitHub Pages builds.
- If customising the plugin fallback page, `_layouts/redirect.html` is the
  documented filename; the plugin provides `page.redirect.to` and
  `page.redirect.from` (NOT the legacy `page.redirect` string).
- Current repository `_layouts/redirect.html` uses legacy page.redirect;
  REPLACE or adapt this layout before routing through `redirect_to`.
- No `_layouts/lists/redirects.html` or `_layouts/details/redirect.html`
  required with the supported plugin; this is a routing exception.
- Existing legacy manual redirects must be catalogued/migrated carefully.
- Verify emitted `_site/hardware/sonata/index.html` contains the expected
  target and fallback link; test real page destination end to end.

REDIRECTS / KRAMDOWN
- YAML-only `_redirects/<slug>.md`; no Markdown body and no front-matter H1.
- Human-authored explanatory content belongs on destination pages, not here.
- Redirect examples use canonical plain YAML syntax; no Kramdown attributes.

17.5 EDITORIAL AND TECHNICAL RULES

- File path is not automatically the public URL; preserve `permalink`.
- If same image is used in multiple pages: assets/images/common/<filename>.
- If a page image is unique: use its owning page assets folder.
- News/event/profile DETAIL content files use _posts/_events/_people etc.
- All image assets for these collection details STILL follow the conceptual
  category/subcategory/slug structure in assets/images/.
- One title from front matter; body starts H2; no breadcrumb Markdown.
- Never duplicate generated citations, prerequisites, schedule, resource
  panels or semantic facts in Markdown; write supplementary context only.
- `summary` shown on lists/detail but not repeated as body prose.
- `navigation.header` is context; does not register every detail as menu link.
- `navigation.footer.category` appears only on pages actually linked in footer.
- Missing optional image = text-only layout, not broken image placeholder.
- Unspecified images/links are omitted, never fabricated.
- User-provided assets are reused and migrated; don't lose diagrams and alt text.
