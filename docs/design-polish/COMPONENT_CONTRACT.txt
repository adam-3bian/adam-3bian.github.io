# CHERI Alliance — Component Design Contract

**Version 1.0 — proposed companion to the Consolidated Content, Template & Forms Specification v5.3**
**Prepared 20 October 2026**
**Status:** Design and implementation proposal; **not deployed**.

## 0. Purpose and source-of-truth boundaries

Create a coherent, responsive component system for the **existing CHERI Alliance content** using the restraint, composition and interaction discipline of [shadcn/ui](https://ui.shadcn.com/) **without turning the Jekyll site into a React application or a generic SaaS dashboard**.

This contract is subordinate to the v5.3 content specification on content ownership, front matter, paths, routing, relationship references, forms, and Markdown authoring. If this contract and v5.3 disagree, **v5.3 controls content semantics**; reconcile visual behaviour before implementation.

**Source material actually examined** (GitHub default branch, 20 October 2026):

- `_config.yml`: real five-category navigation, footer, collection routes, site name, logo assets, theme defaults.
- `pages/index.md`: original homepage headline, audience pathways, featured slides, calls to action.
- `pages/alliance/leadership/members.md`, `_organisations/codasip.md`: directory and real member profile.
- `pages/news-and-events/events-and-archive/upcoming-events.md`, `_events/cheritech26.md`: event list, conference and multi-day programme.
- `pages/news-and-events/people-and-opportunities/speakers.md`, `_people/alastair-beresford.md`: people content and profile.
- `pages/news-and-events/news-and-analysis/latest-news.md`: editorial archive.
- `_guides/choose-a-platform.md`, `_hardware/sonata.md`, `_software/cheribsd.md`: documentation, hardware and software content.
- `_papers/cheriot-complete-memory-safety-for-embedded-devices.md`, `_groups/cheri-zephyr.md`: research and working group content.
- `pages/alliance/membership/contact.md`, `_data/forms.yml`: form preview and external submission flow.
- `_sass/settings.scss`, `_sass/_themes.scss`, `_sass/_base.scss`, `_sass/_header.scss`, `_sass/_navigation.scss`, `_sass/_cards.scss`, `_sass/_hero.scss`, `_sass/_tables.scss`, `_sass/_forms.scss`, `_sass/_site-features.scss`; `_includes/header.html`, `_includes/listing.html`, `_includes/form-fields.html`; `assets/js/navigation.js`, `assets/js/slider.js`.

The repository **currently** has `_news`, `_hardware`, `_software`, inline source breadcrumbs and legacy page layouts. v5.3 **proposes** `_posts`, `_products`, `_repositories`, and `lists/*`, `details/*`, `page/*` layout families. This design contract supports the transition; **do not assume the target model is live**.

**Design rule:** preserve real headings, summaries, dates, affiliations, membership, relationships, verified URLs, images, diagrams and citations. Layout changes must not silently rewrite facts. Examples below use real source titles or content excerpts unless labelled a proposed interface label.

## 1. Design principles and non-goals

1. **Institutional, technical, inviting.** The Alliance is a technical and collaborative organisation, not a sales dashboard. Distinctive CHERI diagrams, logos, hardware, conference photography and research links remain primary visual material.
2. **One visible hierarchy.** Heading scale, spacing, borders and card metadata communicate meaning; large coloured blocks should not carry all the hierarchy.
3. **Light neutral surfaces, branded emphasis.** Use the CHERI teal/ink/mint palette from v5.3 rather than copying shadcn's default black and grey branding.
4. **Progressive enhancement.** All public information, route links and event programme entries remain usable without JavaScript. No essential page content is trapped in tabs or menus that fail closed when scripts are unavailable.
5. **Native Jekyll content.** Liquid includes render semantic HTML. Sass tokens style components. Vanilla JavaScript handles only interactions. No requirement for React, Tailwind, Radix or a front-end framework.
6. **Content-specific, not decorative variants.** A paper, event, member, product and post have different metadata; reuse foundations without forcing one card on everything.
7. **Mobile is a distinct composition.** Use the same content source, not the same desktop flyout squeezed onto a phone.

**Do not emulate:** shadcn dashboard sidebars on ordinary editorial pages; command palettes where no real site search exists; carousels for essential content; placeholder or fake forms; fabricated product badges, statistics or logos; decorative cyber stock photos; complicated multi-level flyouts on touch screens.

**Surface rules:** main reading panels and cards default to opaque white (or dark-theme equivalent), with fine borders instead of multiple translucent blue fills. Do not place all body prose above the tiled hexagon motif. If the motif is retained, confine it to occasional hero/brand bands and keep body text over opaque surfaces. Teal is a **meaningful interactive accent**; mint is not a general foreground colour.

**Typography:** use Poppins 400/500/600; monospace for code. Suggested scale at 16px root: body 16–17px at 1.55–1.65 line height, intro 18–20px, H1 `clamp(2rem, 4.2vw, 3.25rem)`, H2 `clamp(1.5rem, 2.5vw, 2rem)`, H3 1.25rem, card heading 1.125–1.25rem, metadata 0.875rem. Homepage display heading may be larger but must not make secondary pages feel miniature. Text columns max 65–80 readable characters, depending on font and content.

**Spacing:** use the existing 4px-derived Sass spacing steps; 8px within icon/text labels, 12–16px within controls, 24px card padding, 24–32px grid gaps, 40px mobile / 56px desktop between major sections. Set all interactive target areas to **at least 44×44 CSS px** where feasible, with a visible keyboard focus state. This is a design target, not a claim of compliance.

**Breakpoints:** content layout changes based on available space. Proposed navigation mode: mobile/stacked at widths **up to 1100px**, desktop top-level panel from **1101px**. This respects the current `_site-features.scss` tablet override. Verify at 320, 375, 390, 430, 768, 1024, 1100, 1101 and 1440 CSS pixels; also test 200% zoom, narrow landscape and text enlargement.

### 3.1 Navigation Menu — desktop

**Existing content, retained verbatim:** `Discover CHERI`, `Adopt`, `Build`, `CHERI Alliance`, `News & Events`. Top-level groups are sourced from `_config.yml` today; in the v5.3 implementation they must remain centrally configured, not duplicated on page front matter.

**Behaviour/appearance target:**

- White/neutral top bar, intact blue CHERI logo, max site width 1264px, height approximately 72px. Current-brand logo is sourced from `/assets/images/brand/logo-blue.svg` in light mode.
- Top-level labels are calm medium-weight text; focused/open state has an indicator. Use **one anchored broad panel** for mega-menu content rather than cascades of second/third/fourth-level floating menus.
- Discover CHERI has three visible groups (`Why CHERI`, `Understand CHERI`, `Resources`). Adopt has three. Build has four (`Software Developers`, `Technology`, `Platforms`, `Software Ecosystem`). Alliance has four. News & Events has three.
- Group headings non-clickable unless they have verified landing routes; each actual link uses its configured URL. No invented category route. A top-level trigger is a real `button` with `aria-expanded` and `aria-controls`; links remain `<a>`.
- Panel opens on click and keyboard operation; optionally on deliberate desktop mouse hover after validation. Escape closes, returns focus to trigger; outside click closes; moving focus between trigger/panel does not prematurely close.
- Panel never extends past viewport; use scrollable panel at short viewport heights. No opaque shadow obscuring adjacent text.
- Preserve full label text, including `CHERI and Rust - Technical Overview`, `Return an unused Morello Board`, `Privacy`, rather than reducing each to vague icon labels.
- No-JS fallback must expose usable normal navigation, e.g. expanded links or a separate simple index.

**Desktop, using existing Build menu content:**

### 3.2 Mobile Sheet — navigation

- For widths up to 1100px, top bar is a logo and labelled **Menu** control. Trigger opens a right-side panel on medium widths; on narrow phones panel can be full width for readability. Prefer 100dvh (with 100vh fallback), internal scrolling, no body background scrolling.
- Put the same five root categories in a vertical list. Each expands as an accordion to show subcategory heading, then real links. No more than two **visible interaction depths**: root group → grouped links. Retain all content routes even if the presentation simplifies nesting.
- Initial open state: all groups collapsed; expand the chosen category. A link closes the sheet then navigates. Close button, Escape, focus trap/return and labelled state required for JS-enhanced modal version.

### 3.3 Buttons, links and badges

- Buttons: primary (teal background with white text), secondary (white + border), quiet/text and destructive (rare). 44px minimum height; 8px radius; 16px horizontal rhythm. External destinations are **anchors styled as buttons**, not submit buttons.
- A card never needs both a fully clickable wrapper and several nested links. Choose a semantic title link with clear supplementary links, or a single card link; ensure accessible name is meaningful.
- Use original action labels where content provides them (`View event`, `Read article`, `Join the Alliance`, `Open the published Alliance contact form`). Avoid rendering fake `Register` links when the event has no verified registration URL.
- Badges carry short facts only: membership tier/founding member; guide level; event format and computed status. Never badge ordinary section labels. Status labels must have textual meaning independent of colour.
- Source example: Codasip has `Founding member` and `Full Member` in its existing profile; these may become compact neutral/teal badges, not prominent sales ribbons.

### 3.4 Cards: one foundation, five editorial variants

All cards share `border: 1px solid var(--ca-border)`, white surface, 8–12px radius, 20–24px padding, consistent title/summary/metadata spacing, non-jumpy hover and a visible keyboard focus ring. Render cards from **semantic front matter in v5.3**, preserving current-content fallbacks only during migration.

| Variant | Existing concrete example | Source metadata | Media treatment | Mobile |
|---|---|---|---|---|
| News | `A new ETSI standard could rewrite the memory-safety debate` | Date, taxonomy, title, summary | 16:9 existing article image | One column; date above title |
| Event | `CHERITech'26` | Start/end dates, location, format, status, real registration where valid | 16:9 CHERITech graphic | One column; dates/location and single primary action |
| Member | `Codasip` | Organisation, member tier/founding status, summary | Square **contain** logo, never crop the logo | One-column readable cards or two-column logo-only grid with accessible names |
| Person | `Alastair Beresford` | Name, **all** current affiliations, relevant speaker roles | Square portrait; `cover` only with respectful crop | Single column, image 80–96px if compact |
| Technical | `Sonata`, `CheriBSD`, `CHERIoT: Complete Memory Safety for Embedded Devices` | Entity type, short summary, known source links | Diagrams `contain`; may omit image | Full-width rows/cards; long names wrap naturally |

**Fallback:** If an authentic image is absent, render text-only with the same content rhythm, not a random stock illustration or giant empty placeholder. Metadata fields not present in the source are omitted, never guessed.

### 3.5 Breadcrumbs and page headings

- Template-generated breadcrumb trail on every non-home page. Current `source-breadcrumbs` numbered lists in content are **migration-only**; target v5.3 generates the trail from `navigation.header` plus real destinations.
- Desktop: one compact subdued breadcrumb row; mobile: optionally omit middle **visual** crumbs, retain current page context and a navigable immediate parent. Keep full breadcrumb structured data when correct.
- Only one H1. Preserve title and summary; do not repeat identical copy as lede and first paragraph. Do not modify historical `#fragment` links without anchor-alias tests.
- Internal links and cards must continue working through `/hardware/` → `/products/` and `/software/` → `/repositories/` migrations via the explicit redirects specified by v5.3.

### 3.6 Search, filters, grid/list and empty states

**Existing content:** Members, Speakers, Latest News and Upcoming/Past Events directory pages already exist. Their filters/sorts must derive from real member, speaker, category and event data.

- Desktop toolbar: search input left, filter/selects adjacent, view control at right only where both views are implemented. Results count comes from the filtered result set. Sort labels must match actual order.
- Mobile: full-width search, compact filters disclosure/button, visible active-filter count and `Clear filters` action. No dense three-row horizontal controls or select widgets smaller than 44px.
- Empty state: short message (“No members match these filters.”) plus `Clear filters`; do not turn a lack of matches into an apparent data load failure.
- **Membership source-of-truth:** v5.3 `current_members` means `organisation.membership.is_member == true` **and** `organisation.membership.status == active`. Don't infer from `founding_member` or name.
- Event list semantics follow v5.3 status definitions and derived dates; do not hardcode a past/upcoming badge into a static card.
- No fuzzy-search promise unless a real client/server search algorithm is implemented and tested. No Pagination control for an unpaginated list.

### 3.7 Article and technical detail layouts

Keep distinct v5.3 template variants:

- **News/post:** full-width feature image after editorial header; narrower centred prose; publication metadata and author byline; related news cards below. No persistent right fact rail.
- **Event:** event title + image, then concise facts/verified registration; date-grouped multi-day programme; speaker and partner relationships derived. Two-column main/facts about **70/30** desktop; mobile stacks **title → image → essential facts/action → event narrative → all day sections → related**.
- **Person/member/product/repository:** contained portrait/logo/real hardware photo to the right desktop, facts in a small secondary rail when useful. Mobile places image after heading then facts before long body. Non-speaker people and non-member organisations must render **neutral** titles/facts, not fictitious speaker/member labels.
- **Guide:** single readable documentation column, compact level/time/platform metadata strip only if values are actually present. No compulsory right rail or sticky table of contents. Code blocks scroll safely; copy control is optional, not a prerequisite.
- **Paper:** text-first citation and verified publication/download links; no photo requirement. Long author lists wrap and remain selectable/copyable.
- **Policy:** compact no-image heading, prose and document dates/owner where the values exist. No decorative photography.

For long guides and policies, a **contents accordion** on mobile may aid navigation. It must link to stable section IDs and remain optional; do not inject extra headings into content.

### 3.8 Tables, code and sessions

- Desktop technical tables use white cells, thin borders, subtle header background, left alignment and consistent spacing. Do not make every table heading blue-filled.
- Mobile default for genuine comparison matrices: an overflow container with an accessible name and visible scroll cue; do **not** break row/column associations or replace a 12-column specification matrix with misleading independent cards.
- For simple key/value fact lists, use `<dl>` and stacked mobile facts instead of a table.
- The **CHERITech'26** event currently has a two-day programme (12–13 November 2026). v5.3 stores this in `event.schedule[]`; render **all days**, even if optional Tabs are used for convenience. In a no-JS view, show day headings and all sessions in document order.
- Presentations, speaker links, scoped slides/recordings and timezones come from the event's single canonical YAML model, not a second maintained HTML programme.
- Respect `prefers-reduced-motion`; avoid animated layout height shifts during filter/schedule changes.

### 3.9 Forms and newsletter

**Real current content:** contact and newsletter forms in `_data/forms.yml` are preview/external destinations. The current contact page directs visitors to the published Alliance contact form, and asks users not to send sensitive material in a general enquiry.

- **External mode (current + v5.3 sample):** show title, description/privacy guidance and a prominent external link. **No visible local topic/name/email/message fields** and no false `Send enquiry` action.
- **POST mode (future only):** accessible labels, validation, true backend endpoint, success/error response, spam/CSRF controls appropriate to the provider, no secrets in the public repo.
- The newsletter CTA is global, distinct from page-level form definitions and from the site footer. Use a low-emphasis coloured band or bordered panel, not another full-bleed saturated hero. Retain exact editorial text `Stay connected with CHERI` and a valid newsletter destination.
- On mobile, inputs (when legitimate) are always full width, 44px+ targets and legible help/error text. When external, a full-width link button is appropriate.

### 3.10 Homepage — retain the existing story

Use **actual** `pages/index.md` content; don't manufacture feature statistics or rewrite the Alliance's mission.

**Existing hero message:**

> Software runs our world. It deserves stronger security foundations. Enabled by CHERI.

The source also explains that software vulnerabilities have long been a risk and CHERI helps stop vulnerabilities from becoming attacks. Keep that argument in the content-led intro; do not replace it with a generic “The future of cybersecurity” headline.

**Existing audience routes become consistent entry cards:**

1. `Protect your organisation` → pages on vulnerabilities, cost of memory unsafety, strategic case.
2. `Build more secure products` → existing defences, why CHERI, bringing CHERI to products.
3. `Build the technology` → why CHERI, product adaptation, technical getting-started content.
4. `Join the ecosystem` → Alliance overview and member directory.
5. `Meet the community` → news and upcoming events.
6. `Become part of the journey` → existing `Join the Alliance` CTA.

Desktop: hero/lede in one cohesive introductory section, a 3-card row for the first three audiences, a 2-card row for ecosystem/community, and one quiet Alliance CTA panel. Mobile: all cards one column in **source editorial order**; one CTA per group.

The existing `Featured CHERI news and events` slider contains CHERITech'26 and the ETSI article. Preserve both editorial items. **Target recommendation:** turn autoplay off by default or present two visible editorial cards rather than rotating content that users might miss; if autoplay stays, maintain the already-implemented reduced-motion safeguards and provide a pause control. This is an interaction change, **not removal of content**.

### 3.11 Footer and shared editorial CTA

Keep the exact three footer group headings currently in `_config.yml`: **Updates**, **CHERI Alliance**, **Legal**, plus actual social destinations. v5.3 moves footer destination registration to `navigation.footer.category`; render links from that future semantic model without duplicating them in static Markdown.

Desktop: three compact link columns + social area. Mobile: stacked groups with visible headings and reasonably sized links; accordions are optional and should not hide the legal links by default. Do not repeat another large marketing panel immediately after an event's registration CTA.

| `_hardware/sonata.md` | source/collection layouts | `_products`, `details/product` after reclassification | no-crop product media, technical facts, legacy redirects |
| `_software/cheribsd.md` | source/collection layouts | `_repositories`, `details/repository` **only if properly classified** | coherent technology links, real source URLs |
| `_guides/choose-a-platform.md` | guide/source layouts | `details/guide` | narrow reading layout, accessible table, code and diagrams |
| `_papers/...cheriot-complete...md` | source/paper | `details/paper` | exact citation, authors, working publication link |
| `_groups/cheri-zephyr.md` | source/group | `details/working-group` | text-first group description and enquiry CTA |
| `pages/alliance/membership/contact.md`, `_data/forms.yml` | form panel + field includes | `page/form`, canonical external form config | show real external CTA only; preserve privacy/sensitivity guidance |
| shared subscription/footer | `_includes/subscribe.html`, `_includes/footer.html` | Shared prefooter/footer components | fewer coloured blocks, unchanged destinations |

**Migration caution:** don't blindly equate every `_software` record with a source repository; v5.3 explicitly requires classification of software overview/ecosystem pages. Likewise don't substitute an arbitrary shadcn icon for an organisation's brandmark.

## 6. Accessibility, mobile and functional acceptance checklist

### Navigation and focus

- [ ] At 320px, all five primary categories and every configured descendant link remain reachable without horizontal overflow.
- [ ] At 1024px and 1100px, stacked navigation works; at 1101px desktop navigation has enough room for actual Alliance labels, with no clipping.
- [ ] Keyboard Tab/Shift+Tab, Enter/Space, Escape and arrow behaviour are documented/tested; focus doesn't vanish when a submenu or Sheet closes.
- [ ] `aria-expanded`, `aria-controls`, accessible trigger names and close buttons reflect real state.
- [ ] Touch interaction does not require hover; no horizontal flyout chains on phones.
- [ ] A no-JS route to every navigation destination exists.

### Responsive information layout

- [ ] 320/375/390/430px: headline doesn't clip; no card or image is wider than viewport; zoom to 200% remains functional.
- [ ] Organisation logos use `object-fit: contain`; event/news photos use appropriate 16:9 framing; technical diagrams keep full legends and labels.
- [ ] Session/day structure is complete without JS; mobile day sections do not conceal data in inaccessible collapsed states.
- [ ] Technical tables have keyboard-usable horizontal scroll and clear header associations; any mobile card transformation preserves meaning.
- [ ] Genuine 44px touch targets, contrast, visible outlines, accessible link descriptions, form label/help/error relationships.
- [ ] Respect `prefers-reduced-motion`; no mandatory timed content transitions.

### Content parity and trust

- [ ] Original homepage pathways and featured links remain discoverable after redesign.
- [ ] No membership flags, affiliations, papers, session speakers or event statuses are invented.
- [ ] Current member eligibility matches v5.3; non-member organisations and non-speaker people still have neutral profiles.
- [ ] Legacy `/hardware/*`, `/software/*`, news and source fragment URLs keep working per v5.3 migration checklist.
- [ ] External form CTA actually opens the published provider page; never show a fake local submission.
- [ ] All downloadable PDFs and publication links resolve; no placeholder hrefs remain.
- [ ] Poppins and CHERI-owned imagery remain in use; no substituted stock/cyber images.

### Test matrix and methods

Use viewport snapshots and manual keyboard/touch audits for **homepage, Members list, Codasip detail, Speakers list, Alastair profile, Latest News, CHERITech event/list, Guide comparison, Sonata, CheriBSD, Paper, Contact**. Run the actual GitHub Pages/Jekyll build in parallel with HTML validation, automated accessibility checks, keyboard audits and physical mobile-browser testing (iOS Safari and Android Chrome). Accessibility tooling is useful but does not establish complete accessibility on its own.

## 7. Phasing and implementation ownership

**P0 — foundation:** semantic colour/spacing/type/border tokens; header, Navigation Menu, mobile Sheet; one card foundation; breadcrumbs and buttons. Build with existing pages and routes before changing the content schema.

**P1 — public content types:** members/speakers/news/events directories, real variants, filters, event details/schedule, forms external mode, data-led factual badges, responsive tables.

**P2 — technical refinement:** guide and long-form patterns, optional in-page navigation, paper/repository/product/group layouts, slider interaction choice, responsive image tuning, pagination only when needed.

**Migration alignment:** introduce `_includes/components/*` or equivalent as shared implementation pieces, and adapt the existing `_includes/listing.html` and styles gradually; avoid creating a second source-of-truth menu or relationship registry. Apply v5.3's actual YAML migration and URL redirect rules separately and test output parity.

**Definition of done:** a maintainer can change a card or control's design in **one shared component/tokens location**, and the change appears consistently across all relevant real content types; users can find the same information on desktop/mobile with keyboard/touch; no existing information or route is lost.

## 8. Design decisions requiring sign-off before coding

1. **Slider:** keep the current home slideshow with pause/manual controls, or show its featured content as visible cards (both existing stories retained)? Recommendation: visible cards or manual-only carousel.
2. **Menu reveal:** click-only for top-level desktop triggers, or click plus deliberate hover? Recommendation: click-first, with hover tested later.
3. **Dark theme:** retain current dark homepage as a **branded dark hero**, with rest of site in neutral light mode, or support fully switchable dark site mode? Recommendation: branded dark feature/hero first; do not make a theme toggle a prerequisite.
4. **Directory density:** member cards or compact member rows on mobile? Recommendation: one-column full cards for richer descriptions, compact rows for dense browse/search results.
5. **Table treatment:** for each genuine comparison, decide scrollable table vs mobile-reflow facts by semantics; avoid a blanket one-size transformation.

None of these decisions prevents implementing P0 shared foundations.
